# Server host module

Servers interpret games through the Go module `github.com/retrom-project/retrom-runtime/host`, embedded in their
own process. It is the only host implementation: there is no Node host tool, worker process or JSONL service. The
module and the Provider bundles of a release come from the same immutable `vX.Y.Z` tag, so a server pins one runtime
version for both. A development checkout uses a Go workspace that points at the same runtime worktree as its
candidate Providers.

```go
service, err := host.New(providerVersion) // loads the embedded facts once; safe for concurrent use
result, err := service.Call(ctx, "prepare", input) // input is one JSON object; result is JSON
var failure *host.Error                              // Code is a stable RUNTIME_* reason
```

`providerVersion` only labels the projected Provider declarations in `catalog` with the installed release; it never
changes a runtime decision. Each command runs under its own deadline (`host.Deadline`): one hour for
`normalize-content`, one minute for `detect-scummvm` and 30 seconds otherwise, and an earlier caller deadline still
applies. Cancellation returns `RUNTIME_CANCELLED`. Malformed input returns `RUNTIME_REQUEST_INVALID`, an unknown
command `RUNTIME_COMMAND_INVALID`, and any other failure `RUNTIME_REQUEST_FAILED`. A panic inside a command fails
only that request. Only `RUNTIME_PARENT_MISSING` carries details (`parents`). The module owns no sessions, queues,
authorization or network endpoint.

The embedded facts are the runtime JSON facts under `src/runtime/`, the digest-verified arcade DAT facts in
`assets/facts/` and `host/facts/declarations.json`, a projection of the TypeScript Provider declarations generated by
`npm run host:declarations`. `src/providers/*/catalog.ts` stays the only declaration source; `npm run go:check`
fails when the projection is stale.

## Admission

The embedding server bounds concurrency; the module does not queue. Retrom keeps two FIFO lanes: interactive
commands have four execution slots and at most 32 accepted running or queued requests, and `normalize-content` has
two execution slots and at most six accepted requests. Each lane has its own 64 MiB budget for accepted JSON input,
counting running and queued requests, which measures the serialized manifest and locators rather than streamed game
bytes. Requests beyond a lane's count or byte budget return `RUNTIME_BUSY` immediately. Deadlines start before
queueing. A cancelled queued request never runs; a running request keeps its slot until the command returns.

## Commands

- `catalog`: Provider manifests, product bindings, named platforms and static BIOS facts; read once at host startup.
- `storage-layout`: platformId, coreId and saved config; returns `{layout:"ZIP_STORE"|"FILES"}` from the resolved
  binding. The initial project Targets use ZIP_STORE; native archives and other file collections retain FILES. Hosts
  consume this fact rather than maintaining core-name lists.
- `configure`: platformId, coreIds, files, optional evidence/archiveMembers/selection; returns RuntimeConfiguration.
- `discover-content`: immutable files and host-only locators; returns `{files:[{logicalKey,relativeTo,relativePath}]}`
  for bounded, verified single-disc CUE `FILE` references, including references already present in the facts. The
  host skips existing logical keys and authorizes missing files under its source root relative to the original CUE
  source directory before copying their real bytes. Archive members have no external source mapping; missing members
  fail. Discovery never supplies authorization or changes the source file.
- `normalize-content`: platformId, immutable files, locators and a fresh outputRoot; the explicit host-only
  [plugin registry and contract](../host/internal/normalize/README.md) expand supported Electron ASAR, NW executable
  ZIP, Enigma Protector VFS, X'moe PSB and PE32 Molebox 4/STEELBOX containers before resource normalization. Kiri
  CxFilterFS `eliF`, `hnfn`, `Yuzu`, `neko` and `sen:` use statically recovered Tiny/classic Cx parameters; Tiny
  profiles may include a separate first-byte XOR at absolute resource offset zero. Hxv4 archives with a recognized
  supplied bootstrap are converted; see [Kiri import normalization](../host/internal/kirikiri/README.md). Read-only
  probes validate all plans within each phase before conversion; extracted resources and bounded locators feed the
  resource phase. Declared file overlays retain provenance, and independent launch domains, conflicts and matched
  failures stop the operation. All-unmatched input retains its facts for ordinary configuration, identity and shared
  STORE packaging. No native input is executed. Returned final paths are owned host staging state, never game JSON.
- `prepare`: directory, config, files, selected core, fingerprint map, optional savedContext and host-only locators;
  returns identity and resource plans. Arcade inspection reads bounded ZIP central directories. A resource plan
  lists `files`, optional virtual `paths`, and optional `preloadPaths` for files the Target reads before start (MV
  desktop plugin scenarios); the host publishes `preloadPaths` as the file-index `preloadPath` so the browser never
  re-derives which files they are.
- `launch-options`, `kirikiri-entry-candidates`, `rpg-entry-candidates` and `dos-entry-candidates`: read-only entry and
  launch projections described in [runtime configuration](runtime-module.md).
- `arcade-parents`: Parent and media choices for the selected arcade machine, including a proposed attachment.
- `rom-sets`: directory, configuration, immutable files and selected core; returns bounded searchable playable DAT
  entries, the filename match and the selected entry independently of pagination. Optional draft `entryFile`/`romSet`
  affect only this projection. BIOS, device and non-runnable entries are excluded. Labels and versions come from
  digest-verified original DAT during the build.
- `reconcile-config`: validates per-core DAT choices and prunes Parent references that the selected entry no longer
  needs. It returns removed logical keys only after comparing all cores’ references with the previous configuration;
  the host uses its existing transactional retirement and delayed reference-safe cleanup. This is configuration
  validation, not launch preparation or mandatory CRC acceptance.
- `detect-scummvm`: verified providerRoot and a bounded treeRoot; returns candidates and optional automaticSelection.
  The pinned detector from the installed Provider is the only process the module starts.
- `restorable`, `batch-identity` / `batch-restorable`: restore decisions and list identity for up to 10,000 items in
  one call; list identity does not assemble BIOS, Parent or playable resources.
- `bios-requirements` / `bios-identify` / `bios-verify`: resolve declarations (with optional `firmwareEvidence`), or
  identify and verify exact immutable bytes and archive members.
- `batch-content-bios-requirements`: inspect up to 100 ordered items with `directory`, `config`, `files`, host-owned
  `locators`, optional installed `biosFiles`, and an optional allowed `coreId` (directory default otherwise). Each
  result has `{biosRequirements, missingRomMembers, crcWarnings, error}`; arrays are always present and errors are
  stable codes.

Host-only locators have one representation: `{path, offset, sizeBytes}`. The physical absolute path never enters
browser or saved game configuration; standalone files use offset zero. `host/internal/content` opens an independent
descriptor, validates safe integer bounds against the physical object, and supplies logical stat, positional reads and
bounded streams. Evidence, nested native ZIP inspection, ASAR/EXE normalization and project materialization all read
through this boundary. Empty files yield empty streams. A project member is never treated as the complete physical
ZIP, and an adjacent member is never exposed by a read or stream. Path-only external detectors receive a temporary
materialized tree that is removed after the operation. Content identity continues to use logical paths, member
lengths and member SHA values; the host assembles STORE resources itself from the returned resource plans.

Provider release builders and the PFB watcher call `fingerprintProvider` from `scripts/runtime-fingerprints.mjs` with
the current declarations and verified core asset index. Servers read the integrity-covered result from the selected
Provider and pass it to `prepare` as the fingerprint map.

## Rules shared with the browser runtime

Server rules live only in this module. The few facts the browser adapters also need are shared as data, not
reimplemented: the runtime JSON facts under `src/runtime/` (including the RGSS RTP names in `rpg-rtp.json`) and the
generated Provider declarations. Where a browser adapter must still validate the Envelope it receives on its own,
the KiriKiri `engineArguments`/`overlayArchives` options, both implementations assert the same vectors in
`src/kirikiri/target-options.vectors.json`. `tests/catalog-projection.test.ts` keeps the TypeScript catalog projection
used for the generated support catalog equal to this module's `catalog` result.

## Verification

`npm run go:check` runs gofumpt/goimports, the lint policy and source-structure gates of `scripts/go-quality`,
golangci-lint and the Go tests with the same tools, versions and limits as the Retrom backend; lint suppressions are
not allowed. `host/testdata/golden` holds recorded command results over synthetic inputs (`${CASE}` names the case
directory and `${OUT}` a fresh output root). They began as a recording of the retired Node host and are now the
module's regression contract: an intentional contract change updates them with
`go test ./host -run TestGolden -update`, reviewed together with the implementation.
