# Runtime configuration and preparation

The runtime module is the source of game interpretation for both review and play. It declares 110 Provider Targets (75 EmulatorJS and 35 independent runtime Targets), 109 existing product bindings and 95 named platforms. EmulatorJS PPSSPP remains declared without a prior host product binding; the independent PPSSPP Target supplies that product core. These counts describe retained declarations, not completed product acceptance.

`RuntimeConfiguration` contains `content` and optional `cores`. Content identifies a single file, arcade archive, DOS bundle and optional internal executable, or a project. RPG Maker projects select the actual one of seven engine implementations. Per-core rules contain only declared Target options and arcade Parent logical paths. BIOS file IDs, installation state, import batches, deployment revisions and authorization credentials never enter this JSON.

`configureRuntime` constructs these rules from immutable logical path/size/SHA facts and bounded evidence. RPG Maker uses its real JS marker, Game.ini Scripts field or LCF system identifier. DOS selects an actual executable member when one is explicit or uniquely detected. A package with several programs omits `entryPath` and starts the core's program menu; an explicit `entryPath` must be nonempty and identify a real archive member. Empty strings and null are invalid configuration states. ONS, KiriKiri and Cave Story choose their ordinary script/archive/executable entries. ScummVM runs the pinned native detector and returns explicit candidates; a blocked or ambiguous candidate requires an operator choice rather than a host engine guess. Every stored core option is validated against its actual Target schema before returning a configuration.

`prepareRuntime` selects the declared implementation using directory platform, selected core and game content. It freezes coreId, providerId, targetId, coreFingerprint and romHash, then returns selected options, checkpoint semantics, BIOS requirements, actual arcade dependencies and generic resource plans. The host projects these plans into authorized resource URLs. `paths` maps logical file keys to virtual paths; `encoding: "ZIP"` requests an ordinary deterministic STORE archive. MKXP receives the complete project ZIP, DOS receives its ZIP as `game.zip`, file-tree cores receive paths relative to the project root, and a single CUE receives its verified referenced track files. Multiple Parent archives are merged into one validated archive, with conflicting same-path bytes rejected. The runtime mounts the named ZIP intact for arcade driver lookup; the core loader must not expand it into loose ROM members.

ROM identity is calculated from the entire Game active file set, including Parent files needed by any configured core. A single non-project ROM uses its raw SHA-256. Projects, including singleton trees, and multi-file content use the canonical sorted logical path, byte size and SHA-256 tree encoding. Media rows remain outside this set. Selecting another core does not change the Game content identity.

BIOS requirements have stable explicit keys, known size and digest facts, delivery paths and activation options. Requirements share a file only where declarations explicitly share the same key. A scan matches known digests or an unambiguous declared name/path when no digest is known; hosts skip ambiguous missing requirements. Arcade DAT facts inspect actual ZIP members, accept merged content and identify missing Parent and firmware sets even if the game rules omit them. The compressed fact table retains each pinned source digest in `src/runtime/arcade-provenance.json`; it contains metadata, never ROM or firmware bytes.

For Beetle PSX HW, playable preparation reads only the disc system area (at most 11,760 bytes) from the managed locator. Its sector-four license selects the declared Japanese, US or European firmware requirement; the region never becomes stored game JSON. Unknown compressed-disc evidence leaves all declared regional files optional for the core to select from the available installation, so it does not invent a Japanese default. The stable firmware names, sizes and MD5s follow the [core's official firmware declaration](https://docs.libretro.com/library/beetle_psx_hw/).

EasyRPG converts the authorized public file-tree index into the pinned engine's private index and scoped XHR aliases. The canonical host index URL remains unchanged; every game payload still goes through shared Content IO. Tyrano's isolated bridge redirects desktop file-storage calls to the engine's own browser-storage functions before initialization. This preserves its missing-value and serialization rules without editing the managed project or adding an engine branch to the host.

The actual Target fingerprint hashes a separately compiled selected Provider execution branch plus its declared execution assets. Release labels, deployment bundle digests and unrelated adapter branches are excluded. Native XML/data assets are included when declared for execution. Source pruning fails explicitly when the expected dispatch boundary no longer matches. Regression tests use the actual build algorithm to prove repeated builds agree, another adapter does not change the Target, its own adapter/core bytes do, and the public checkpoint codec changes every affected Target. Provider bundles publish these identities in `runtime-fingerprints.json`; PFB loose descriptors publish the current Target map and manifest atomically.

Restore requires exact frozen core/provider/Target, actual fingerprint, complete content hash and current checkpoint format. `prepare` accepts an optional `savedContext` with the eight frozen Save extinfo fields. It first checks the current directory permits the saved core, the actual implementation and whole active content still match, and the format is readable. It then validates and prepares the frozen content rules and runtime options rather than the game's edited options. A raw single-file identity permits a filename change: its original entry is mapped to the sole current file after its SHA matches. Project trees remain path-sensitive. DOS program selection and ScummVM detector options use this same boundary; the host supplies facts and does not interpret the engine.

Theodore exposes optional `thomsonModel` with its native model choices. Omitting the option, or selecting Auto, uses the pinned core's original filename detection order. Preparation resolves that to a concrete model in runtimeOptions (the native no-match default is TO8), without adding an inferred model to Game JSON. The source is [Theodore autodetect_model](https://github.com/retrom-project/theodore/blob/5ba20e4fd598f6a008689867d20537f397a9783f/src/autostart.c#L144). The editable game title never selects a computer model. Saved options retain the original model even after the game configuration changes.

ONS host capture is available only at a stable native dialogue wait with fully drawn text/background, outside menus, transitions, skip and automatic playback. Its native save entry atomically rechecks that condition and serializes the current wait, page, UTF-8 text offset, font cursor and textgosub continuation rather than an earlier user-slot savepoint. Restoring the same instance or a new one continues at that wait; ordinary in-game slots keep their original semantics and serialization buffer. Busy capture returns the existing public `BUSY` reason. The current core must export `_onsyuri_host_checkpoint_ready`; the adapter does not supply a default for missing ABI. Only the current public single-gzip checkpoint format is read. Runtime URLs are deployment facts and do not participate in save compatibility. A server losing a short-lived run context must never reconstruct a prior draft with a current hash; the host preserves the original immutable save context and checkpoint bytes until durable storage confirms the matching save.

The browser consumes one `createRuntime(envelope, host)` and `PlayerRuntimeV1`. Existing login state authorizes HTTP resources. Run IDs identify resource scope; message nonces correlate RPC. Isolated web projects load their explicit entry through the host shell and bounded STAT/READ bridge, including ordinary relative script/import/Worker/media paths. There are no derived tickets, tokens or runtime cookies. Review can restore an explicit LOCAL descriptor whose bytes are returned by the host; ordinary saves use HTTP descriptors.

## Offline host tool

The npm package layout contains `scripts/runtime-cli.mjs`, its host helpers, `dist/runtime/**`, immutable JSON facts and `assets/facts/**`. With production dependencies installed and Node 24, it runs offline without a Git checkout, esbuild or a separate service. Release builds also produce `retrom-runtime-host-tool-<tag-version>.tar.gz` with that complete layout, production dependency closure and source digest. The host must publish the complete layout as an immutable tool snapshot; running requests must not read a dist directory that an active build cleans. Its catalog and selected Provider manifests come from the same build.

Commands read one bounded JSON request on stdin and write one JSON result to stdout:

- `catalog`: Provider manifests, product bindings, named platforms and static BIOS facts; read once at host startup.
- `configure`: platformId, coreIds, files, optional evidence/archiveMembers/selection; returns RuntimeConfiguration.
- `discover-content`: immutable files and host-only locators; returns `{files:[{logicalKey,relativeTo,relativePath}]}` for bounded, verified single-disc CUE `FILE` references, including references already present in the facts. The host skips existing logical keys and authorizes missing files under its source root relative to the original CUE source directory before copying their real bytes. Archive members have no external source mapping; missing members fail. Discovery never supplies authorization or changes the source file.
- `normalize-content`: platformId, immutable files, locators and a fresh outputRoot; retained Electron ASAR and NW executable ZIP containers become ordinary web project files through bounded streaming extraction. It never executes native bytes. Returned path is host staging state, never game JSON; the host imports those exact new facts before configuration. Ordinary content returns its unchanged file facts.
- `prepare`: directory, config, files, selected core, fingerprint map, optional savedContext and host-only locators; returns identity and resource plans. Arcade inspection reads bounded ZIP central directories.
- `detect-scummvm`: verified providerRoot and a bounded treeRoot; returns candidates and optional automaticSelection.
- `assemble-resource`: files, locators, optional virtual paths and a fresh outputPath; streams a deterministic STORE ZIP, verifies every file SHA and removes incomplete output on failure.
- `parent-archive`: immutable archive files and locators; merges bounded verified members into one archive.
- `batch-identity` / `batch-restorable`: process up to 10,000 items in one invocation; list identity does not assemble BIOS, Parent or playable resources.
- `bios-requirements` / `bios-identify`: resolve declarations or identify exact immutable bytes and archive members.

The same executable accepts `--serve` for an internal host process pool. Each newline-delimited request is exactly `{id, command, input}`; id is a nonnegative safe integer or 1–128 printable ASCII characters without spaces, and input is an object. Each reply is `{id, result}` or `{id, error}`. A worker executes one request at a time and waits for stdout backpressure before reading another; requests and responses are limited to 64 MiB each. Domain or malformed-message errors do not discard the next request. An oversized input terminates the worker with an error, and EOF ends the process after any final complete JSON message. The host owns a small process pool, includes queue time in deadlines and kills/replaces a worker when a request is cancelled or times out. Workers retain only loaded code and immutable catalog facts: they do not own sessions, durable queues, authorization or a network endpoint.

Provider release builders and the PFB watcher call `fingerprintProvider` from `scripts/runtime-fingerprints.mjs` with the source and development esbuild dependency. The offline host tool reads the integrity-covered result from its selected Provider. Hosts cache startup facts and bound repeated preparation work; they do not launch one Node process per save.

Unit and build gates validate this contract and all retained adapters. Product acceptance remains a separate per-binding exercise: real review and play, frame/input evidence, declared checkpoint semantics, a different run's restore and post-restore input. Isolation URL loading and loss-of-context draft persistence need actual browser and host fault evidence. A component test, missing-material annotation or declaration count is never a product pass.
