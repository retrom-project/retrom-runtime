# ONScripter, KiriKiri and TyranoScript

| Platform / core | Target | Input | Runtime requirements |
| --- | --- | --- | --- |
| `ons` / `onscripter_yuri` | `onscripter-yuri` | `ONS_PROJECT`, delivered as a file tree | Same-origin Wasm runtime |
| `kirikiri` / `kirikiri2` | `kirikiri2-kag` | `KIRIKIRI_PROJECT`, delivered as a file tree | Threaded Wasm and cross-origin isolation |
| `tyranoscript` / `tyranoscript` | `tyranoscript` | `TYRANOSCRIPT_PROJECT`, delivered as isolated web content | Isolated game origin and content bridge |

Keep the selected project's script/archive and referenced images, audio and other assets together. All three Targets use managed Content I/O with on-demand loading and explicit full preload. [SiglusEngine](siglus.md) is a separate integration with its own format and browser requirements.

## ONScripter Yuri

Configuration selects a real `nscript.dat`, `nscr_sec.dat`, `0.txt` or `00.txt` entry. The Target requires an explicit `scriptEncoding` of `gbk`, `sjis` or `utf8`; the host passes runtime-generated options without duplicating encoding rules. Configuration detects it from the script the engine actually reads in the entry directory (`0.txt`, `00.txt`, `nscr_sec.dat`, then `nscript.dat`): the host supplies at most the first 1 MiB of each such script as bounded evidence, the runtime removes the file's obfuscation and chooses UTF-8 when the text decodes cleanly, otherwise GBK or Shift_JIS by decoding errors and kana frequency. Existing games keep their stored option until their content is replaced. The core reads project files by byte range through shared Content I/O (`ons-content-io-v1`): opening a large archive such as `arc.nsa` fetches only the ranges the engine reads, and the second launch reuses the cached blocks. Native media playback retains its own browser boundary. Empty auxiliary files, including version markers, remain in the project tree with size zero and do not prevent startup.

The Target declares `GAME_SAVE`. Save to a normal slot inside the game, then synchronize the native save directory to the platform. A successful native `writeSaveFile` callback, after both the slot and its compatibility sidecar have been written, enables synchronization. Startup, settings writes, and dialogue or rendering state do not create progress. The adapter does not call the host instant-save API or create a hidden slot.

The explicit native format is `ons-game-save-v1`, with the public single gzip storage wrapper. It retains the complete native save directory, including ordinary slots, `.compat` sidecars and global/settings files. Restoration imports these files before ordinary engine startup; open the game's LOAD menu and choose a slot. It does not automatically resume a script continuation. Before a completed native save availability is `NO_SAVE`; restored or successfully synchronized progress is `UNCHANGED`. Acknowledgment covers only the exported revision, leaving later native saves pending. A normal game exit exports confirmed, changed progress without invoking SAVE or LOAD. Existing platform saves are retained; formats outside the current declaration are shown as unavailable for restoration.

## KiriKiri2 KAG

Configuration selects a `startup.tjs`, `data.xp3` or another actual `.xp3` entry. Bounded XP3 header evidence also identifies archives with other suffixes. All candidates first determine the containing project root, before entry types are ranked: a root archive outranks a nested copy's `startup.tjs`, and peer roots require an explicit selection even when their entry types differ. Within the chosen root, `startup.tjs`, `data.xp3`, signature-backed `data.*`, then other archives retain their priority; multiple candidates in the same tier still require a choice. An explicit selection can choose any valid candidate, including a nested project. A selected archive becomes `startupXp3Path` regardless of its suffix; a loose root `startup.tjs` starts its directory. Project resources remain relative to the selected root. The saved launch options and checkpoint format remain unchanged.

Host import normalization can convert verified CxFilterFS `eliF`/`hnfn`/`Yuzu`/`sen:` variants into ordinary XP3 before configuration. Names and optional salts come from the archive; supported Tiny/classic Cx parameters come from static PE data/code relationships in supplied EXE/DLL/TPM files. These files are never executed. Successful normalization preserves archive layering and returns new immutable content facts; source metadata anomalies are explicit diagnostic details, not complete-source integrity passes. Ordinary XP3 is retained unchanged. Hxv4 name recovery remains unsupported: no plugin matches it, so ordinary entry recognition and validation decide import success. Matched CxFilterFS with missing parameters, extra filters or ambiguous profiles fails; titles do not select conversion rules. See [normalization contract](../runtime-module.md).

The Kiri file tree preserves exact paths, including names that differ only in case. Its virtual filesystem enumerates both names and resolves an exact name first; a case-folded alias is usable only when it is unique. Other Targets retain their explicitly declared folded uniqueness requirements. A Wasm trap, abort or nonzero process exit reports a fatal failure and closes the session; only a zero process exit requests normal exit. An unhandled native script exception reports bounded script, line and trace information through the core callback. Exceptions handled by the game and ordinary localized dialogs do not independently cause fatal failures.

This is the maintained KAG integration. Arbitrary KiriKiri/Z, native DLL plugins and archive protection schemes require their own verified support.

Disc dependency discovery follows the selected single-file Target's declared formats. Incidental CUE files in project content stay opaque. Disc CUE parsing accepts explicit Unicode BOMs or strict UTF-8; legacy Shift-JIS/GB18030 candidates must agree on references or resolve uniquely against actual tracks. Ambiguous missing legacy names fail with `RUNTIME_CUE_ENCODING_REQUIRED`.

The Target declares `GAME_SAVE`. Save to a normal slot inside the game, then sync the native files to the platform. Before exporting confirmed progress, the core calls a registered native system-data flush callback to persist late save-menu metadata. A restored session imports those files before ordinary engine startup; the player opens the game's LOAD menu and selects the slot. The adapter never creates a hidden bookmark or automatically loads a scenario. The [KAG bookmark contract](https://krkrz.github.io/krkr2doc/kag3doc/contents/SaveData.html) restores a scenario label, which is insufficient to promise an arbitrary UI or execution-state snapshot.

The core observes completed native KAG `saveBookMarkToFile` calls without replacing their original behavior. Actual nonempty writes within a successful call establish progress; unrelated settings alone do not enable synchronization. File names and extensions are opaque: a thumbnail container can also contain the bookmark data. The bundle retains complete final files at their original virtual paths, related settings and database overlays, and deletion records. Failed or incomplete native writes cannot be published as a successful capture. A confirmed capture acknowledges only its own revision, so subsequent writes remain pending. Before a native save the status is `NO_SAVE`; an already synchronized revision is `UNCHANGED`.

The explicit native format is `kirikiri-game-save-v1`, with the public single gzip storage wrapper. Web SQLite writable files use their original virtual file paths, so ordinary existence checks, deletion and restored native files share one object. Archive members remain read-only. The native file layout uses the existing GAME_SAVE v1 contract. It does not read development-only hidden SQLite sidecars or the previous automatic-bookmark format. Existing save records are not deleted or silently converted. Games that bypass the observed KAG native save API require their own verified support; filenames do not select an alternative saving implementation.

A confirmed game exit notifies the adapter before Web teardown. The adapter stops polling the native save observer, drains the active JSPI frame, then calls the core's native-exit finalizer to flush system data and detach the observer before releasing TJS objects. Final capture includes teardown writes from the complete virtual-filesystem overlay. A zero process exit also exports confirmed, changed progress. Neither path invokes a native SAVE or LOAD command. No progress or an unchanged revision exits without a placeholder; incomplete writes, a failed flush or a failed final export report an error and preserve the previously stored save.

## TyranoScript

The entry is the selected project's `index.html`. Scripts, assets and media run in the isolated game origin through the content bridge. The adapter redirects supported desktop-storage calls to the engine's own browser storage before initialization; it does not execute a desktop package or expose a general Node.js environment.

The Target declares `INSTANT` snapshot semantics. Snapshot capture and restoration use the engine bridge and stable execution points. Plugin compatibility and script behavior need per-project validation, including restoring in a different instance and continuing input.
