# Daphne candidate Target

The candidate `daphne` Target loads a `DAPHNE_PROJECT` through the shared Content I/O session. The ROM ZIP, framefile, DAT, and OGG members are materialized through Content I/O; the M2V is opened with the shared bounded Range reader. The fork runs its MPEG decoder on a pthread. Emscripten normally proxies that thread's synchronous `fd_read` to the browser main thread; suspending the proxied callback with Asyncify reports a short read before the Range request completes. The fork's pthread bridge waits on a shared result while the main thread obtains bytes from the runtime reader, then fills the shared Wasm buffer and resumes the caller. The ordinary EmulatorJS external-file loader is not used for game media.

The current detector and adapter accept a flat project with one ZIP, a matching TXT framefile, one referenced M2V, and small companion files. A single authorized `interstellar.daphne` sample passed local directory upload, Review Preview, approval, Product Launch, animated video, gamepad Select/Start, and bounded 206 Range checks. This does not establish support for multi-video or ZIP-less Daphne projects. Core and Provider are still local candidates until the release chain and formal package verification complete.

The fork reports `retro_serialize_size() == 0` and rejects serialize/unserialize. The user explicitly allowed Daphne, and only Daphne, to use `NO_SAVE`; this Target declares `saveSemantics: "NO_SAVE"`, `checkpoint: null`, and `capabilities.checkpoint: false`. NVRAM and score files do not restore the current scene. Other Targets keep their save requirements. Replace `NO_SAVE` only after native progress restoration works across distinct launches.
