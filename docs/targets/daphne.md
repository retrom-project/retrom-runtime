# Daphne Target

The released `daphne` Target loads a `DAPHNE_PROJECT` through the shared Content I/O session. The ROM ZIP, framefile, DAT, and OGG members are materialized through Content I/O; the M2V is opened with the shared bounded Range reader. The fork runs its MPEG decoder on a pthread. Emscripten normally proxies that thread's synchronous `fd_read` to the browser main thread; suspending the proxied callback with Asyncify reports a short read before the Range request completes. The fork's pthread bridge waits on a shared result while the main thread obtains bytes from the runtime reader, then fills the shared Wasm buffer and resumes the caller. The ordinary EmulatorJS external-file loader is not used for game media.

The current detector and adapter accept a flat project with one ZIP, a matching TXT framefile, one referenced M2V, and small companion files. Multi-video and ZIP-less Daphne projects are outside this supported shape. The [EmulatorJS source catalog](../../src/providers/emulatorjs/source-catalog.ts) fixes the immutable core release, commit and asset digests.

The fork reports `retro_serialize_size() == 0` and rejects serialize/unserialize. This Target declares `saveSemantics: "NO_SAVE"`, `checkpoint: null`, and `capabilities.checkpoint: false`; the host must present that save limitation. NVRAM and score files do not restore the current scene. Save support requires native progress restoration across distinct launches, not a placeholder checkpoint.
